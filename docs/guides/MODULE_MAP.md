# Module Map

> Where to put new code. Read this before adding features or message handlers.

---

## Architecture

`project.js` is a thin coordinator. It wires modules together and dispatches messages. All logic lives in dedicated modules following the `attachXxx(ctx)` pattern.

### Rules

1. **Never add inline logic to project.js handleMessage.** Find the right module and add it there.
2. **500 line limit per module.** If a module grows past 500 lines, split it.
3. **All new modules use the `attachXxx(ctx)` pattern.** Accept dependencies via ctx, return a public API object.
4. **Mutable state uses getters/setters in ctx.** Never capture a primitive that might change later.

## Server-side Modules (lib/)

Account sign-in: `account-login-page.js` serves the progressive account chooser and its explicit public assets in `public/auth/account-login.*`. `account-remembered.js` stores browser-bound account hints server-side, addressed by a rotated opaque HttpOnly cookie; successful session issuance remembers up to five accounts for 90 days. `/auth/accounts` lists only that browser's previously authenticated accounts and supports same-origin forgetting. These hints never authorize access. Server PIN and administrator setup retain their existing pages.

Session metadata: `account-session-store.js` records browser User-Agent and last observed IP on authenticated activity. Migration timestamps remain internal expiry anchors, never historical activity claims; `server-account-security.js` exposes unknown activity as null and sorts the current session first. `user-settings-sessions.js` groups unobserved migrated sessions behind a disclosure. New session issuance atomically replaces only the presented cookie for the same account, without merging sessions by IP or User-Agent.

Server PIN is legacy single-user authentication only. In account mode (`users.isMultiUser()`), `server-auth.js` rejects the legacy `/auth` endpoint, `project-server-settings.js` and daemon web/IPC callbacks reject Server PIN changes, and `server-settings.js` hides/disables the entire PIN section after `/api/me` confirms mode. Account mode is independent of account count; migrated owner account PINs remain supported. Stored legacy hashes are retained, not deleted.

Personal device management: `public/modules/user-settings-sessions.js` expands browser sessions inline in Personal settings → Account, using store-backed request state, local sign-out confirmation and `/api/account-sessions`. Opening the list never navigates away; only confirmed current-session sign-out returns to sign-in. The standalone `account-session-page.js` route remains available for direct links.

Account session security: `account-session-store.js` persists hashed tokens and browser metadata, migrates existing token maps with one-time grace, and enforces 30-day absolute / 7-day idle account expiry. `server-account-security.js` owns session listing/revocation and administrator connection settings; `account-session-page.js` provides personal browser-session management. `account-auth-socket.js` checks revocation/expiry without extending idle time for outbound events or heartbeat messages. `account-auth-throttle.js` persists bounded account/IP attempt budgets across restarts. `account-auth-transport.js` requires HTTPS (localhost setup exception), validates same-origin authentication writes and trusts forwarded protocol/client address only from configured exact proxy peers. `public/modules/account-transport-settings.js` edits proxy trust in Server settings. Legacy solo/Server PIN access remains compatible. `test/account-security.test.js` covers migration, expiry, revocation, persistence failures, throttling, transport and expiring one-use operator recovery; the browser fixture supports `--sessions`.

Account creation lives in `users-create.js`, wired by `users.js`. Legacy server-PIN migration persists account mode and a tagged credential together; `users-server-pin.js` verifies those tagged credentials and scopes older untagged copies to the recorded migrated owner and matching config hash. `users-auth.js` upgrades verified credentials on login without rejecting a valid PIN when the upgrade write fails. `test/users-pin-auth.test.js` covers login, PIN changes, persistence failures and migration compatibility.

Account password policy: `account-auth-policy.js` persists the one-way account PIN-to-password policy in users data, excluding solo anonymous and sole migrated Server PIN installations. `server-account-passwords.js` handles administrator activation, PIN-proven restricted enrollment, password sign-in and changes; `account-passwords.js` owns bounded asynchronous scrypt. `server-auth.js` binds password sessions to the current credential and rejects legacy session issuance under password policy. `account-auth-socket.js` stops existing workspace socket traffic when authorization changes. `account-password-page.js` owns the standalone sign-in/enrollment/change form; `public/modules/account-auth-settings.js` adds the direct policy selector and explicit activation review to Server settings. Existing account PINs authorize enrollment only after activation; credential persistence precedes PIN removal, and recovery resets require enrollment again. Email-only accounts need a temporary account PIN before policy activation. Coverage: `test/account-password-transition.test.js`; isolated visible fixture: `test/fixtures/account-password-server.cjs`.

Account passkeys: `account-passkey-policy.js` stores a separately configured exact HTTPS origin and hostname RP ID (HTTP localhost development exception); network allowlists and request headers never expand this trust. `server-account-passkeys.js` verifies WebAuthn through SimpleWebAuthn, persists named per-account credentials and counters, and requires fresh passwords for management. `account-passkey-challenges.js` owns expiring, browser-bound, single-use challenges; registration also binds the existing session and password. Password-enrolled accounts can add optional passkeys, with required user verification and password fallback. Recovery clears passkeys; `server-auth.js` rejects sessions tied to removed credentials. Server setup lives in `public/modules/passkey-server-settings.js`; personal management in `account-passkey-page.js`, using the shared standalone shell and the ES module `public/modules/passkey-browser.js`. That module is also served publicly at `/auth/passkey-browser.js` for login. `test/account-passkeys.test.js` uses real synthetic P-256 signatures; the isolated browser fixture supports `--password --virtual-passkey` without using real credentials or a device keychain. Authenticator TOTP remains out of scope.

### project.js (thin coordinator, ~1,200 lines)

Wires all modules, sets up session manager and SDK bridge, dispatches messages.

### Private Clay and Mate ownership

`users-permissions.js` treats Mate projects and sessions as owner-only, without ordinary-project administrator or sharing exceptions. Runtime access records in `server.js` and `server-palette.js` carry `isMate`; `workspace-query-access.js` requires the caller's Mate registry membership. `sessions.js` forces private creation/restoration and rejects sharing/ownership changes. `session-visibility.js`, `project-sessions.js`, `server-admin.js`, and daemon access setters reject sharing or transfer. `server-mates.js` scopes lifecycle broadcasts to the owner, `server-settings.js` protects custom avatar reads, and `mates.js` keeps registry ownership immutable. Coverage: `test/mate-private-ownership.test.js` and the Mate case in `test/worktree-access-server.test.js`.

Mate tool parity matrix: owner/project authorization is the common gate; a Mate receives only tools whose target and credentials remain bound to its private project/session.

| Capability | Clay/project session | Mate session | Boundary |
|---|---|---|---|
| Remote MCP, Linear, GitHub, Notes, Markdown presentation, shared browser, email, debate | Yes | Yes where the session-bound handler authorizes | Owner credentials and project/session target stay server-derived |
| Workspace/history, Mate Knowledge, Mate tool control | No or scoped differently | Yes | Mate registry membership and canonical Clay-only curation remain enforced |
| User Knowledge curation, Project Logs/Issues, session spawn/handoff, autonomous Driver orchestration | Yes where eligible | No | Canonical Clay, Driver, project-target, and cross-session ownership boundaries |
| Chrome-extension browser bridge | Yes when extension connected | No | Existing bridge is project-wide and lacks a private Mate/session target; use shared browser for Mate access |
| Project Scheduled Task authoring | Yes for eligible project Drivers | No | Creates project Driver/Worker pairs; excludes Mates |
| Scheduled Mate messages and resumed tool execution | Yes | Yes for eligible owner-private chats | Existing message scheduler dispatches through the same SDK/query tool guards; authoring project tasks is a separate capability |

### Mate message scheduling

`mate-schedule-input.js` validates optional creation intent and existing-chat proposals against `schedule-rule.js`; reviews show the actual server timezone. `project-mate-creation-proposal.js` records the validated intent in the human creation card. Only its authenticated approval reaches `server-mates.js`, which registers the ready owner-private Mate and binds the intent through its real session manager, with failure cleanup.

`mate-scheduling.js` provides query-bound interview, proposal, list/read/update/cancel tools for ordinary private Mates. Creation, update and cancellation use server-owned structured approval cards (`mate-schedule` source); model flags and chat text cannot authorize them. `mate-schedule-lifecycle.js` persists logical IDs, config revisions, occurrence identities, delivery counts and terminal states in session metadata. Cancellation saves its tombstone before occurrence cleanup. The producer uses durable session origin with explicit legacy identity lookup, supports independent Mate occurrences, and checks the logical lifecycle again before release and consumption. Queue consumption is reconciled after restart; missed times coalesce into one admitted delivery and then the next future occurrence. Provider execution across a process crash is not exactly-once.

`project-scheduled-message-queue.js` holds shared queue correlation helpers; `project-scheduled-messages.js` retains ordinary scheduled-message semantics. `server-home-chat-events.js`, `server-home-mcp-consent.js` and Home transcript controllers share the same authenticated question path with project chat. `yoke/session-tool-transport.js` and `sdk-bridge.js` expose native Claude tools and the exact-query bridge for resumed Codex catalogs. Project Scheduled Tasks remain unavailable to Mates. Production-path regression: `test/mate-scheduling.test.js`; isolated production UI/WebSocket fixture: `node test/fixtures/mate-scheduling-browser-server.cjs 27159`; repeatable browser regression: `node --test --test-force-exit test/mate-scheduling-browser.test.cjs`.

### Owner-private User Knowledge (Me)

`user-knowledge-service.js` projects the separate append-only `user/<owner hash>/you` collection. Projects and Mates submit evidence-backed observations; only the owner’s canonical Clay can save, revise, decline, or archive them. `project-user-knowledge.js` binds read/report/curation tools to live sessions and handles authenticated `you_*` reading/reporting messages. `server-user-knowledge.js` schedules bounded, hidden Clay review turns through the owner’s Default AI, drains pending batches, retries failures with a limit, and resumes durable reports after restart. Saved-change notifications go only to the owner; pending/declined observations never announce a saved memory.

Private knowledge uses the personal-connection session guard, including Worker ancestry and foreign input. Reading it marks the conversation (and its Driver) owner-only; the marker survives restore/fork and prevents sharing/ownership transfer. Canonical Clay’s built-in registry identity is immutable through Mate updates. SDK/native/exact-query MCP tools share the handlers; resumed Codex catalogs recover through the session bridge. `public/modules/you.js` reuses Logs list/detail rendering and workbench sizing, opened by Me in the first Clay sidebar tool slot. The palette registry marks Me fixed and Clay-only: saved ordering and hidden preferences cannot move or remove it, drag sorting skips it, and dynamic Knowledge inserts after it. The header retains its standard dimensions; mobile Tools also exposes Me. `you-activity.js` owns temporary, queued typewriter announcements in place of the idle Clay Studio wordmark and paginated activity history; `public/css/you.css` adds local styles. Server-persisted per-owner seen revisions power the Me unread badge and New/Updated row labels; only authenticated human acknowledgement of a rendered revision clears it, never agent reads. Owner-scoped change notifications refresh other devices without replaying a saved-memory announcement. Internal `you_*` identifiers remain stable. Entry comments reuse the Logs discussion UI and persist as owner-private observations with Clay’s review decision; the list has no composer. Correction/forget requests are observations for Clay; archival stops retrieval/context use while append-only audit records remain. Coverage: `test/user-knowledge*.test.js` and existing session/access/SDK regressions.

### Infrastructure Modules

`project-mcp.js` owns owner-scoped computer routing, discovery/import messages and managed connection wiring. Computer registries are namespaced by the real storage root; source-manager socket membership, current user/project authorization, host connection and replacement identity remain mandatory. Calls use the source project's sender and slug. All project contexts live in the server process (`server.js` → `createProjectContext`); vendor subprocesses return through authenticated HTTP bridges.

`mcp-connection-store.js` provides encrypted atomic snapshots: `snapshot()` returns records and revision together; `save(records, revision)` replaces the complete owner managed catalog and this project's computer preferences, preserves other projects exactly once, and rejects stale revisions. Migration is once per project; deletion tombstones prevent later legacy migrations from resurrecting removed servers. Identical historical duplicates are repaired, conflicting duplicates fail closed. Exclusive file locks encompass migration and CAS across processes; contention fails with retry feedback. A lock left by an abruptly terminated writer needs operator recovery after verifying the writer is gone; no automatic stale-lock removal is claimed. Encryption keys are published atomically before readers can observe them.

`mcp-source-adapters.js` normalizes JSON/JSONC/TOML/YAML frontmatter and configured ACP name/value arrays. `mcp-source-discovery.js` reads only owner-authorized files, reports provenance/duplicates/conflicts/unsupported formats and rechecks source hashes and catalog revision before import. `mcp-import-credentials.js` substitutes explicitly supplied Clay credentials without reading vendor token stores or referenced files. Discovery and import never start configured commands or contact services; imports are disabled until human Enable/Test. Plugin state comes from Claude installed registry/settings and Codex config plus its upstream installed-version selection (`local` first, otherwise the greatest version); unknown or ambiguous state blocks import. `mcp-tool-policy.js` preserves allow/deny policies (Copilot `tools`, Qwen `includeTools`/`excludeTools`, camel/snake aliases, empty allowlists) in SDK catalogs and direct calls. Malformed and unknown server fields require reviewed direct configuration rather than silent import. Existing configs remain unchanged. Shared installations need mapped OS users for home discovery/local execution; the SDK transport uses `setpriv`, failing closed if it cannot apply OS identity.

`mcp-remote-connections.js` owns managed stdio, Streamable HTTP and SSE execution, checking live owner/catalog state before and after network work and before OAuth mutations. It disconnects stale configurations and suppresses late revoked results; failed calls are not replayed. `mcp-local-transport.js` starts explicit stdio activations with an owner environment. `mcp-oauth.js` owns Clay PKCE login, while `mcp-network.js` / `mcp-browser-proxy.js` enforce public-network access. `mcp-query-bridge.js` exposes current-query external tools: fresh Codex uses dynamic definitions; resumed Codex and ACP use exact-generation stdio bridges; Claude receives SDK MCP. `mcp-proxy.js` preserves schemas; `mcp-session-access.js` preserves private-session, foreign-input and Worker ancestry guards. `public/modules/mcp-discovery-view.js` adds scan/import and redacted credential requirements to the existing MCP workbench, with state and messages in `mcp-ui.js`.

### Where to add a new server HTTP endpoint

1. Identify which concern it belongs to (auth? admin? skills? settings?)
2. Add the handler in the matching module's `handleRequest` function
3. If no module fits, add it directly in `server.js` appHandler or create a new `server-*.js` module

### Where to add a new message type

1. Identify which concern it belongs to (session mgmt? filesystem? loop? etc.)
2. Add the handler in the matching module's `handleXxxMessage` function
3. If no module fits, create a new one following the `attachXxx(ctx)` pattern
4. Wire it in project.js with a single `if (module.handleXxxMessage(ws, msg)) return;` line

### Where to add a new HTTP endpoint

Add it in `project-http.js` inside the `handleHTTP` function.

## Extraction Pattern Reference

```js
// lib/project-example.js
var fs = require("fs");

function attachExample(ctx) {
  var cwd = ctx.cwd;
  var send = ctx.send;

  // Module-private state
  var counter = 0;

  function handleExampleMessage(ws, msg) {
    if (msg.type === "example_increment") {
      counter++;
      send({ type: "example_count", count: counter });
      return true;
    }
    return false; // not handled
  }

  return {
    handleExampleMessage: handleExampleMessage,
  };
}

module.exports = { attachExample: attachExample };
```

`project-server-settings.js` handles authorized, validated daemon-setting mutations, and `daemon-settings.js` persists before publishing live configuration. `server-notification-settings.js` provides authenticated account preferences; `public/modules/notification-settings.js` owns Personal notification saves and device status. Server-wide instruction editing was removed; existing project/OS-owner instruction files and agent consumption remain untouched. See `docs/design/server-settings-system.md` for the capability map and save/effect contracts.

### Server disk usage

`server-storage.js` exposes authenticated administrator-only `GET /api/server/storage`, coalesces concurrent scans and caches results for 30 seconds. `storage-usage.js` measures allocated filesystem blocks across Clay data, registered projects and mapped Linux home directories using metadata only; Linux OS-user multi-user mode resolves ownership by UID; other modes group project sizes by registered owner without scanning homes. Overlapping roots/hard links count once, conflicting ownership is unattributed, and unavailable identities/partial scans are explicit. Scans prioritize projects, skip symlinks/nested mounts and continue in the background with HTTP 202 progress until completion. Only directory and hard-link identities are retained for deduplication. `public/modules/server-storage-settings.js` owns the Storage & retention usage table and refresh/status behavior with state in `store.js`.

### Primary linked work

`session-work-primary.js` persists one user-selected URL per Linear issue, GitHub issue and PR type in session `workPrimary` metadata. `project-session-github.js` handles owner-authenticated `session_work_primary_set` messages for all types. Link/refresh operations preserve selections; unlink refuses a saved primary. Explicit agent `primary:true` link requests use the server-owned structured human confirmation before changing selection, with owner/access/selection revalidation. `public/modules/session-work-primary.js` renders grouped popover choices and correlated save feedback; `session-github.js` prefers saved selections when rendering badges.

### Browser links in chat

`public/modules/clay-browser-links.js` renders explicit `[label](browser:https://example.com/)` destinations as compact globe pills through `markdown.js`. Clicking opens the embedded desktop Browser panel; ordinary web links and code samples retain their current behavior. `pane-browser-bridge.js` forwards only validated live same-project split-pane clicks to the host. `shared-browser.js` handles the user activation and availability feedback; `project-shared-browser.js` validates URLs and live authorization, reveals matching pages, coalesces pending opens, and creates a new tab for other destinations. Full navigation URLs stay private for exact matching; public `browserLink` values omit query/fragment. The browser skill and tool prompt teach the explicit Markdown format.

### Project ownership and administrator metadata

`project-ownership.js` prepares deterministic ordinary-project ownership recovery and persists before runtime publication. `server-path-access.js` bounds directory picking and registration by canonical paths. `project-directory-claim.js` reserves new create/clone destinations atomically, rejects registered-path intersections, and limits failure cleanup to the claimed directory identity. `project-push-access.js` applies live project/session authorization to push delivery. `project-admin-overview.js` owns the allowlisted administrator projection and content-free Overview/Access document; its client controller and CSS use the matching name under `public/modules/` and `public/css/`. `public/modules/project-access-recovery.js` clears revoked content and resolves reconnect destinations. See `PROJECT_OWNERSHIP_ACCESS.md` for policy, recovery and the OS authority boundary.
