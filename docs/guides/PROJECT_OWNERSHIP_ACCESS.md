# Project ownership and administrator access

Account role and project content authorization are separate. An administrator can inspect an ordinary project's allowlisted display name, owner, visibility, viewer access and registration status. A foreign private project's strip link and deep link render a dedicated Overview/Access page. This page opens no project socket and loads no transcript, file, terminal or application content modules. Resource usage is explicitly unavailable until a reliable project aggregate exists.

Content requires a real account plus ownership, public project visibility or an explicit project/worktree grant. Session visibility is checked separately: private sessions belong to their individual account, including within public projects. Project ownership transfer never transfers session ownership. Clay and Mate projects remain owner-only and have no administrator overview.

Only a valid project owner can transfer ownership or change visibility/sharing. Owner IDs must resolve to existing accounts and cannot be cleared. The application refuses account deletion while registered ordinary projects still belong to that account, including projects whose directories are currently unavailable. Administrator PIN reset of another account and arbitrary OS identity reassignment are disabled because they could bypass the content boundary through impersonation. Server-side credential recovery and verified OS provisioning remain separate operations.

At daemon startup, after account bootstrap and before project registration, `project-ownership.js` prepares a copy of the configuration. Valid explicit owners and all visibility/share settings are preserved. Ordinary public orphans use a persisted designated existing administrator, preferring the recorded legacy bootstrap owner when available. Otherwise administrator IDs are sorted for deterministic selection. Private orphans require a unique account mapping from authoritative OS identity, a matching filesystem UID and a real project path within a real home. Symlink aliases, shared UIDs, overlapping homes and unresolved identities are rejected. Ambiguous records retain their original ownership evidence and are marked **Ownership needs recovery**, with content disabled. Worktrees inherit their parent's access and recovery state. Clay/Mates and historical private session owners receive no administrator fallback.

The migration publishes its result only after the existing atomic configuration save succeeds. Failure aborts startup before projects are registered. Repeated runs are idempotent. No recovery UI can claim an ambiguous private project; the next action is independent verification of the account's OS mapping followed by a successful startup repair. A pre-account configuration is left untouched until account bootstrap.

Create and clone reserve their destination using a non-recursive atomic directory creation before Git initialization or ownership changes. Existing directories, files and symlinks are rejected. Canonical destinations cannot coincide with registered projects, contain registered projects, or fall within another owner’s registered root. Failed attempts clean up only when the destination still has the filesystem identity created by that attempt; replacements are retained.

Directory picking and project registration use real paths. Another account cannot register a private project, its child, its parent or a symlink spelling as a newly owned project. With multiple accounts and no OS-user mode, directory picking is limited to authorized project roots; creating a fresh project remains available. OS-user mode uses the resolved account home and applies the same role-independent foreign-root restriction.

HTTP, project WebSocket admission, per-message access, session lists/history/search, workspace-query authorization and notification snapshots/live delivery use the content predicates. Project push previews are scoped by the same live project/session checks, and unread reminders are targeted per account. Hub schedules are owner-filtered; removed-project records without an account owner are withheld from account viewers. Project-list broadcasts substitute allowlisted metadata for foreign administrator entries. Session and project revocation close affected sockets; the client clears the rendered document before leaving. Reconnect checks membership again before opening a replacement project socket.

## Machine authority boundary

These are application authorization rules. A machine/root operator who can read or change Clay's files, credentials, process environment, source code or OS accounts remains outside this boundary. A user who legitimately has a terminal or agent execution capability can exercise the underlying OS account's filesystem authority; strong separation of those processes requires distinct OS users and OS permissions. Application administrator status alone does not grant foreign project/session content through the application APIs. This change does not claim isolation from root, arbitrary server code execution or credentials obtained outside Clay.

## Verification fixture

`node test/fixtures/project-list-access-server.js` starts the actual production server and UI with temporary `HOME` and `CLAY_HOME` set before imports. It prints its temporary URL. `/__fixture/admin` and `/__fixture/owner` sign into test-only accounts; these routes exist only in the fixture. External presentation libraries are served locally where required; unused diagram/terminal integrations are mocked. Adapter initialization and model/completion calls are mocked; model turns are disabled. Stop the process to remove its temporary home.

`RUN_OWNERSHIP_BROWSER=1 node --test --test-force-exit test/project-admin-overview-browser.test.js` verifies strip selection, network boundaries, deep-link reload, the informational Access tab, a narrow viewport and independent owner access. The browser fixture is stopped by test cleanup.
