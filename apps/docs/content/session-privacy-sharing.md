# Session privacy and sharing

Session visibility is checked separately from project access. A public project can contain private sessions. “Public” means visibility within the authorized Clay Studio workspace; it does not turn a session into an anonymous internet page.

## Check a session's visibility

1. Open the intended project and session.
2. Open its session menu or information controls.
3. Inspect the visibility/sharing option available to you.
4. Confirm the intended change.
5. Check the updated state before inviting someone to open it.

Project and session default visibility controls are available in the relevant settings. Defaults govern new work; inspect an existing session rather than assuming a changed default rewrote all history.

Private sessions belong to their individual owner. Project ownership transfer does not transfer ownership of private sessions. Ordinary administrator status is not a general right to read foreign private transcripts.

## Share a task

The recipient first needs access to the project. Then the session must be visible to them under its own access rules.

For a joint investigation, use a shared project session and place the relevant context there. If the original task is private, summarize only material you intend to share. A copied link does not override access checks.

When joining a live conversation, confirm which account owns it and whether you can send messages or approve actions. Presence shows participation; it does not itself grant new permission.

## Mates and private context

Projects and conversations belonging to Clay or another Mate are owner-private and have stricter boundaries than ordinary projects. Do not expect a project administrator or teammate to open a Mate conversation through a shared link.

Likewise, [Me](/docs/mate-knowledge-memory-me) is owner knowledge, not a project-wide database of personal information. Keep private observations out of a shared [Log](/docs/project-logs) or Note unless you intentionally choose an appropriate summary.

## Access problems

If a recipient sees an access refusal, check the project grant, session visibility, signed-in account, and current ownership. Do not solve it by making the whole server anonymous.

Revoked access can close an existing connection. Reconnecting rechecks access; a browser that previously displayed content is not continuing authorization.

See [Project sharing](/docs/project-sharing), [Users and roles](/docs/team-users-roles), and [Account security](/docs/account-devices-security).
